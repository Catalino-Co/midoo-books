La base técnica es sólida y el producto ya cubre el ciclo completo (escribir → maquetar → previsualizar → exportar en 5 formatos). Lo que falta para producción no es funcionalidad, sino empaquetado, integridad de datos, seguridad y pulido de la experiencia.

Fortalezas para conservar

Esto ya está bien resuelto. Conviene no romperlo al refactorizar.

Arquitectura

  • Tres capas con reglas de importación explícitas. El core editorial está en TypeScript puro y es testeable.
  • IPlatformAdapter desacopla la UI de Electron, lo que deja abierta una versión web.
  • contextIsolation: true y nodeIntegration: false. La API del preload es tipada y no expone ipcRenderer completo.
  • Migraciones versionadas (v1–v11) con tabla schema_migrations.

Producto editorial

  • Motor de paginación propio con medición DOM, control de viudas y huérfanas, y recto/verso.
  • Tipos de sección con presets editoriales (TOC, folio, cabecera, página derecha).
  • Cinco exportaciones (PDF pantalla/impresión, EPUB 3, DOCX, Markdown) con historial.
  • Modos Escribir / Maquetar / Enfocar, atajos visibles y contador de palabras.

Calidad de base

  • vite build y el bundle de Electron compilan sin errores.
  • tsc --noEmit de la app web da 0 errores y los 4 tests pasan.
  • Documentación de arquitectura, desarrollo y manual de usuario en el repo.
  • Commits pequeños con mensajes descriptivos.

Bloqueantes para producción (P0)

Cada punto incluye la evidencia encontrada. «Verificado» significa que lo reproduje ejecutando el código; el resto viene de leer el código.

P0-1

La app empaquetada abre en blanco

Verificado en build
Evidencia
El build/index.html que genera adapter-static (el fallback SPA) importa scripts con rutas absolutas: import("/_app/immutable/entry/start….js"). En producción, electron/main/index.ts usa loadFile(build/index.html), así que esas rutas apuntan a file:///_app/… (la raíz del disco). paths.relative no aplica al fallback.
Impacto
El instalador generado con npm run dist muestra una ventana vacía. El repo no tiene build/ ni release/, lo que sugiere que el flujo empaquetado aún no se ha probado.
Solución
Servir la app con un protocolo propio con privilegios (app://midoo/) y un fallback SPA. Esto también da un origin estable para el export a PDF (P0-2) y permite una CSP real. 
protocol.registerSchemesAsPrivileged([{ scheme: 'app', privileges: { standard: true, secure: true, supportFetchAPI: true } }]);
protocol.handle('app', async (req) => {
  const { pathname } = new URL(req.url);
  const file = path.join(BUILD_DIR, path.normalize(decodeURIComponent(pathname)));
  const inside = file.startsWith(BUILD_DIR + path.sep);
  const target = inside && existsSync(file) && statSync(file).isFile() ? file : path.join(BUILD_DIR, 'index.html');
  return net.fetch(pathToFileURL(target).toString());
});
mainWindow.loadURL('app://midoo/library');
Otra opción es el router por hash de SvelteKit (kit.router.type = 'hash'), aunque el protocolo propio es más robusto.
P0-2

La exportación a PDF falla en producción y confía en una URL que envía el renderer

Evidencia
export.service.ts:497 envía baseUrl = window.location.origin, que bajo file:// vale "file://" o "null". exports.handlers.ts construye `${baseUrl}/export-render/…` y abre esa URL en una ventana oculta con el preload completo. Si la ventana falla, no se destruye (win.destroy() solo se llama si todo sale bien), y si se cumple el timeout de 15 s se imprime igual, posiblemente incompleto.
Impacto
El PDF, que es el entregable principal, no funciona en el instalador. Además, cualquier URL que llegue por IPC recibiría acceso a window.electronAPI.
Solución
Que el proceso main construya la URL (app://midoo/export-render/{id}) e ignore baseUrl. Usar try/finally para destruir la ventana. Si se cumple el timeout, devolver un error claro en vez de un PDF parcial. Mostrar el progreso al usuario.
P0-3

Integridad de datos: claves foráneas inactivas y escritura no atómica

Verificado
Evidencia
  • No se ejecuta PRAGMA foreign_keys = ON, así que los ON DELETE CASCADE del esquema no hacen nada. Prueba: tras books:delete, la sección y el bloque del libro siguen en la BD. La carpeta de medios userData/books/{id} tampoco se borra.
  • persist() reescribe la BD completa con writeFileSync en cada escritura (25 llamadas). Si la app se cierra o se va la luz a mitad, el archivo queda corrupto, y no hay copia de respaldo.
  • Las migraciones no usan transacciones: si una falla a medias, el esquema queda inconsistente.
  • Si openDatabase() falla, el error se ignora («modo degradado») y el usuario ve una biblioteca vacía sin explicación.
Solución
Activar foreign_keys al abrir la BD. Escribir de forma atómica (archivo temporal, fsync y rename) con debounce y copias rotativas (por ejemplo, las últimas 10 más una diaria). Envolver cada migración en BEGIN/COMMIT y hacer un backup antes de migrar. Si la BD falla, mostrar un diálogo con opciones (reintentar, restaurar respaldo, abrir carpeta). A medio plazo, conviene evaluar better-sqlite3 con WAL: electron-builder recompila módulos nativos con install-app-deps, lo que elimina la razón original para usar sql.js.
P0-4

Superficie de seguridad en IPC y Electron desactualizado

Verificado
Evidencia
  • fs:readFile y fs:listFiles aceptan rutas absolutas arbitrarias. Prueba: fs:readFile('/etc/hostname') devuelve el contenido. El comentario dice lo contrario.
  • assets:importPaths copia cualquier ruta que envíe el renderer. En resolveBookStoragePath, bookId no se valida.
  • No hay Content-Security-Policy. Además, sandbox: false (innecesario: un preload con sandbox puede usar contextBridge e ipcRenderer), setWindowOpenHandler permite abrir ventanas que no son http y no hay guarda en will-navigate.
  • Electron 31 ya no recibe parches de seguridad (la versión estable actual es la 45.x) y npm audit lo marca como «high».
Solución
Eliminar fs:* genéricos y sustituirlos por operaciones de intención (abrir .md mediante un diálogo que devuelve el contenido, no la ruta). Validar los argumentos de IPC con zod o valibot y comprobar event.senderFrame.url. Añadir CSP, sandbox: true, bloquear navegación y ventanas nuevas, activar los Fuses de Electron (RunAsNode off, cookies cifradas, ASAR integrity) y actualizar a una versión soportada de Electron.
P0-5

Empaquetado y distribución incompletos

Evidencia
  • electron-builder usa build/ como carpeta de recursos por defecto (ícono, instalador), y esa es justamente la salida de SvelteKit. Tampoco hay ícono definido.
  • No hay firma de código: Windows SmartScreen mostrará «Editor desconocido» y muchos usuarios abandonarán la instalación.
  • No hay auto-update, changelog ni canal de versiones, y solo hay target Windows.
  • extraResources incluye content/ejemplo-libro.md, que es contenido de la fase de prototipo.
Solución
Configurar directories.buildResources: "resources" con íconos .ico, .icns y .png. Firmar con un certificado OV/EV o con Azure Trusted Signing en Windows, y con notarización en macOS. Añadir electron-updater con un feed en GitHub Releases o S3 y un pipeline de CI que construya en matriz (win/mac/linux) al crear un tag.

Antes de una beta pública (P1)

No impiden instalar, pero sí afectan a la confianza, la mantenibilidad o la calidad del libro resultante.

P1

Calidad y CI

  • svelte-check reporta 10 errores y 15 avisos. Uno es un bug real: onMount(async …) en el editor devuelve una función de limpieza que Svelte ignora, así que el listener de keydown se acumula en cada visita.
  • El tsconfig de Electron reporta 95 errores (parámetros any en el preload, el alias $lib no se resuelve, falta lib: dom). esbuild no comprueba tipos, por eso pasan desapercibidos.
  • Solo hay 4 tests, todos del importador. Faltan tests del motor de paginación, la numeración, el TOC, las migraciones y comparaciones de exportación contra archivos de referencia.
  • Configurar CI en cada PR: typecheck, svelte-check, vitest, build y Playwright E2E.
P1

Monolito del editor

  • content/+page.svelte tiene 5.896 líneas (unos 203 KB) y mezcla estructura, lienzo, modo escritura, inspectores por tipo de bloque, drag & drop y autosave.
  • Propuesta: dividirlo en StructurePanel, BlockCanvas, WriteSurface e Inspector/* por tipo, con estado en editor.svelte.ts (runes) y comandos centralizados. Esto también facilita implementar deshacer/rehacer.
P1

Código heredado del prototipo

  • Quedan las rutas /book/[slug] y +page.server.js con fs y prerender, processMarkdown.js, static/book-styles.css, la dependencia pagedjs (reemplazada por el motor propio) y sus estilos .pagedjs_page en app.css.
  • El build genera un __data.json y páginas prerenderizadas que no se usan.
P1

Fuentes: lo que ves no siempre es lo que imprimes

  • El catálogo ofrece fuentes del sistema (Calibri, Cambria, Book Antiqua, Garamond…) que no existen en todos los equipos, y el medidor usa Georgia como base. La paginación cambia según la máquina.
  • En las pruebas (equipo sin Georgia), el editor cayó a una serif y la vista previa a una sans.
  • Propuesta: incluir fuentes OFL (EB Garamond, Crimson Pro, Literata, Source Serif 4, Libre Baskerville, Inter) con @font-face, usar las mismas en el medidor y embeberlas en PDF y EPUB.
P1

Importación Markdown incompleta

  • Las listas y el énfasis (**negrita**, *cursiva*) se importan como texto literal y así aparecen en la vista previa (ver captura). Un libro real necesita al menos cursiva, negrita y listas.
  • La página «© 2026…» se clasificó como «Sección especial» en lugar de Derechos o Créditos. La heurística puede detectar «©» o «derechos reservados».
P1

Dependencias, observabilidad y rendimiento

  • npm audit: 46 vulnerabilidades. En producción: js-yaml (vía gray-matter) y nanoid (vía docx). En desarrollo: vite, vitest, concurrently y electron-builder.
  • Hay 27 console.log. Usar electron-log con rotación, un reporte de errores opt-in y un botón «Exportar diagnóstico».
  • Probar con un libro de 300–500 páginas: tiempo de paginación, memoria y tiempo de persist(). Si hace falta, paginar de forma incremental o en un Worker.
P1

EPUB conforme

  • dc:identifier usa el UUID sin urn:uuid:. Añadir dcterms:modified, portada (properties="cover-image") y metadatos de accesibilidad.
  • Validar en CI con EPUBCheck y Ace (DAISY). Desde el 28 jun 2025, la European Accessibility Act exige ebooks accesibles para vender en la UE.
P1

Documentación desalineada

  • ARCHITECTURE.md lista sections.handlers.ts y blocks.handlers.ts, que no existen (están en books.handlers.ts).
  • DEVELOPMENT.md indica el puerto 5173, pero el configurado es el 5178.
  • Falta un README, una licencia, un CHANGELOG y una política de privacidad.

Análisis UX/UI

Capturas de la UI real con el backend real (repositorios e IPC en Node) y un libro de ejemplo importado desde content/ejemplo-libro.md. Se revisó a 1440 px y a 1024 px (el ancho mínimo de la ventana) y se pasó axe-core con reglas WCAG 2 A/AA.

Lectura general

El tema oscuro es coherente y la navegación por módulos (Descripción → Contenido → Assets → Estilos → Maqueta → Vista previa → Exportar) sigue el flujo editorial real, lo cual es un acierto. El problema principal es la densidad: en el editor conviven tres columnas fijas más la barra lateral global, con seis controles en la cabecera. Esto deja poco espacio al texto, que es lo que más importa al autor. El segundo problema es que muchas pantallas muestran lenguaje interno (null, Folio físico, Sección especial, Font size, Assets) en lugar de lenguaje editorial.

1 · Editor de contenido

Alta

Panel Estructura ilegible

Los títulos se cortan a 5–6 caracteres porque el asa, la estrella, el badge «138¶» y las acciones comparten unos 235 px. En la sección activa el badge se superpone al título.

Propuesta: mostrar las acciones solo al pasar el cursor o con foco, títulos en 2 líneas con tooltip, panel redimensionable y numeración de capítulo visible (Cap. 1, 2…).

Alta

No escala a 1024–1280 px

La cabecera se solapa y el centro se estrecha. Las laptops de 13" trabajan justo en ese rango.

Propuesta: por debajo de 1280 px, colapsar la barra lateral global a iconos y convertir el inspector en un panel flotante. Agrupar Markdown, Enfocar y Vista previa en un menú «⋯».

Media

Modo Maquetar trunca el texto

Cada párrafo se muestra en una sola línea con «…» y con mucho padding. No se puede leer ni revisar el contenido en ese modo.

Propuesta: mostrar 3 líneas y la opción de expandir, o una vista de tarjetas compacta con palabras y páginas estimadas por bloque.

Media

Sin deshacer y con confirmaciones nativas

No hay deshacer/rehacer global, y las acciones destructivas usan confirm() del sistema («esta acción no se puede deshacer»).

Propuesta: una pila de comandos con Ctrl+Z / Ctrl+Shift+Z, eliminación con toast «Deshacer» y snapshots automáticos (la tabla snapshots ya existe en el esquema pero no se usa).

2 · Vista previa paginada

Alta

Calidad tipográfica del texto justificado

El CSS fija hyphens: none. En español, con columnas de A5, justificar sin guionizar produce «ríos» de espacio en blanco: es el primer detalle que nota un editor profesional.

Propuesta: lang="es" en la página, hyphens: auto o Hyphenopoly (patrones TeX para español) tanto en el medidor como en el render, y text-wrap: pretty en los párrafos.

Media

Texto interno visible

«SECCIÓN ESPECIAL» y «Folio físico 1» no deberían aparecer en una página de créditos. La cabecera debería usar el título del libro o del capítulo, y las páginas preliminares no llevan cabecera.

Media

Navegación y feedback

  • Las miniaturas solo muestran «R 1 / L 2», sin contenido. Mejor usar miniaturas reales o el título de la sección.
  • Falta una vista de doble página (spread), esencial para revisar recto/verso.
  • Hay que pulsar «Recargar» a mano. Mejor recalcular automáticamente con debounce e indicar «Actualizado hace 2 s».
  • Falta un panel de avisos de paginación: viudas, huérfanas, páginas casi vacías e imágenes con poca resolución.

3 · Estilos, Maqueta y Exportar

Media

Estilos sin vista en vivo

Se editan números a ciegas: hay que guardar, ir a la vista previa y recargar. Propuesta: mostrar a la derecha un párrafo de muestra que cambie al instante, presets con nombre («Novela clásica», «Ensayo moderno», «Infantil») y controles de tipo slider con valores sugeridos.

Media

Maqueta abstracta

Hay ocho campos numéricos (formato, márgenes, sangrado y zona segura) sin representación visual. Propuesta: un diagrama de doble página que se actualiza con los valores, presets de plataforma (KDP, IngramSpark, Lulu) y avisos («en KDP, un libro de 400 páginas requiere un margen interior ≥ 15,9 mm»).

Media

Exportar sin preflight ni progreso

Falta un resumen previo (páginas, fuentes, imágenes, avisos) y una barra de progreso. Al terminar, conviene ofrecer «Abrir archivo» y «Mostrar en carpeta». Las promesas de cada formato deben coincidir con lo que hace hoy.

Baja

Crear libro y Biblioteca

Al crear un libro no se pregunta el formato ni la plantilla, ni se ofrece importar el manuscrito. La biblioteca solo muestra iniciales, sin búsqueda ni orden, y sin progreso (palabras o páginas). Propuesta: un asistente de 3 pasos (Datos → Formato y plantilla → Manuscrito) y tarjetas con portada real, conteo y fecha de última edición.

Ideas y mejores prácticas que agregan valor

Ordenadas por impacto para el usuario objetivo (autor independiente y pequeña editorial hispanohablante).

Diferenciador Tipografía en español de verdad

  • Comillas latinas automáticas «» y “ ”, y conversión de -- a raya de diálogo (—) con su espaciado correcto.
  • Guionización española, letra capital, versalitas en la primera línea de capítulo y espacios finos.
  • Corrector ortográfico es-ES nativo de Electron (session.setSpellCheckerLanguages) y aviso de palabras repetidas.

Diferenciador Listo para imprenta y plataformas

  • Presets de KDP, IngramSpark, Lulu y Bubok: formato, sangrado de 3,175 mm y margen interior según el número de páginas.
  • Calculadora de lomo según páginas y tipo de papel, con generador de portada completa (frente, lomo y contra) y código de barras ISBN.
  • Informe de preflight: imágenes por debajo de 300 ppp, fuentes no embebidas, páginas en blanco, viudas y huérfanas, y conteo de páginas par.

Confianza Tus datos, seguros

  • Formato de proyecto portable .midoo (zip con BD y medios) para mover, compartir o respaldar.
  • Historial de versiones con snapshots automáticos y comparación «antes/después» por capítulo.
  • Respaldo opcional en una carpeta sincronizada (OneDrive, Dropbox o iCloud).

Productividad Flujo de escritura

  • Paleta de comandos (Ctrl+K) para saltar a capítulos, insertar bloques o cambiar de módulo.
  • Metas de palabras por día o capítulo, estadísticas y tiempo de lectura estimado.
  • Notas al pie y finales, listas, tablas simples, bloque de verso/poesía e índice analítico.
  • Comentarios y marcas de revisión para trabajar con un corrector.

Alcance Plantillas y onboarding

  • Plantillas de libro completas (estilos, maqueta y secciones preliminares): novela, ensayo, poesía, infantil y memorias.
  • Un libro de ejemplo precargado al primer arranque y un tour guiado de 5 pasos.
  • Importación de .docx, además de Markdown, porque la mayoría de manuscritos llegan en Word.

Opcional Asistencia con IA (opt-in)

  • Borrador de sinopsis, texto de contraportada y descripción para tiendas.
  • Sugerencia de texto alternativo para imágenes, lo que ayuda a cumplir la accesibilidad del EPUB.
  • Revisión de coherencia de nombres y fechas. Siempre con control explícito del autor.

Operación Mejores prácticas de producto

  • Versionado semántico, changelog visible en la app («Novedades») y canal beta.
  • Telemetría anónima opt-in de eventos clave (crear libro, exportar, errores) para priorizar con datos.
  • Licencia y EULA, aviso de licencias de terceros y fuentes, política de privacidad y canal de soporte.

Plan sugerido

Las duraciones son orientativas, para un desarrollador a tiempo completo.

Fase 0 · Desbloquear el instalador (1–2 semanas)

P0-1 protocolo app:// → P0-2 export PDF desde main → P0-3 foreign keys, escritura atómica y backups → P0-4 cierre de IPC, CSP, sandbox y actualización de Electron → P0-5 recursos de build, ícono y firma. Cierra con un smoke test manual del .exe en una máquina limpia.

Fase 1 · Calidad y quick wins UX (2–3 semanas)

CI con typecheck, svelte-check, tests y build. Limpieza de código heredado. Fuentes OFL embebidas y guionización. Estructura legible y layout que funcione desde 1024 px. Contraste AA. Textos 100 % en español. Ocultar las etiquetas internas en la vista previa. Negrita, cursiva y listas en la importación.

Fase 2 · Beta cerrada (3–4 semanas)

5–10 autores reales con sus manuscritos. Deshacer, snapshots y proyecto .midoo. Preflight y presets KDP. Auto-update. Recoger métricas de exportaciones exitosas y fallidas y de tiempo hasta el primer PDF.

Fase 3 · Lanzamiento 1.0

Builds para macOS (notarizado) y Linux, EPUB validado con EPUBCheck y Ace, plantillas, asistente de creación, sitio web y documentación de usuario.
